# In-App Auto-Update — Design Spec

**Date:** 2026-07-29
**Status:** Approved (pending implementation)
**Branch:** `feat/app-updater`
**Related:** `.github/workflows/release.yml`, `docs/notes/*` (release pipeline)

## Goal

Add in-app update detection and installation via the **Tauri v2 Updater
plugin**, so users on an older build can discover a newer version, download it,
and replace their running app — without manually visiting the GitHub Releases
page. Distribution stays zero-infrastructure: the existing `release.yml` +
`tauri-action` pipeline already builds bundles; this adds the signed manifest
(`latest.json`) and the client-side check/install flow.

## Decisions (locked)

| Decision | Choice |
|---|---|
| Update check trigger | **Auto on startup** (silent, fire-and-forget) + **manual re-check** button in Settings |
| Startup-check error handling | **Silent** — network/signature errors are swallowed (offline machine is a first-class case); only "update available" surfaces to UI |
| Manual-check error handling | **Visible** — errors show inline in the Settings modal (user clicked, so they're watching) |
| Release publishing | **Auto-publish** — `releaseDraft` flips `false`; `latest.json` goes live when CI is green |
| Install flow | **Two-step** — "Check" shows version; "Download & install" is a separate explicit click |
| Update endpoint | `https://github.com/pndaza/just-ocr/releases/latest/download/latest.json` (auto-generated by `tauri-action`) |
| Distribution infra | **None new** — GitHub Releases serves the manifest + signed bundles |
| Signing | Required keypair; private key in GitHub secret, pubkey string in `tauri.conf.json` |
| Relaunch | `@tauri-apps/plugin-process` `relaunch()` (cross-platform; Windows auto-exits on install) |
| Surfacing "available" | **Accent dot on the Settings gear** (Toolbar) — no new toast system |
| New Rust commands | **None** — frontend drives via the `@tauri-apps/plugin-updater` JS API |
| New persisted state | **None** — no localStorage, nothing to remember between sessions |

## Relationship to the "fully offline" identity

`AGENTS.md` frames just-ocr as **"fully offline … no internet, no system
installs."** That promise is specifically about **OCR**: models are bundled in
the binary via `include_bytes!`, recognition runs entirely on-device, and no
cloud API is ever consulted to recognize text. An update check is fully
compatible with this — it is a separate, occasional concern (discovery of newer
builds), not part of the OCR pipeline. A machine with no network still OCRs
exactly as before.

Two properties keep the update path well-behaved regardless of connectivity:

1. **Startup check is silent and fails soft.** An offline user sees nothing —
   no error, no spinner, no degraded UX. The check is best-effort: success
   surfaces an available update; any failure is swallowed to `console.warn`.
2. **No telemetry.** The updater hits exactly one endpoint (the GitHub Releases
   manifest). There is no analytics, version ping-back, or usage reporting —
   the only network call is fetching `latest.json`, and only to learn whether a
   newer build exists.

## Architecture

### Plumbing (Tauri v2 Updater)

```
┌─────────────── Frontend (Svelte/TS) ───────────────┐┌──── Rust (Tauri) ────┐
│                                                    ││                     │
│  src/lib/updater.ts                                ││  src/lib.rs run():  │
│   ├─ checkForUpdate(onResult)                      ││   tauri_plugin_     │
│   │    → @tauri-apps/plugin-updater check()        ││     updater         │
│   │    → maps result → UpdateStatus                ││   tauri_plugin_     │
│   ├─ downloadAndInstall(onProgress)                ││     process         │
│   │    → update.downloadAndInstall(onEvent)        ││                     │
│   │    → @tauri-apps/plugin-process relaunch()     ││  (no new commands)  │
│   └─ getAppVersion() → @tauri-apps/api app.version ││                     │
│                                                    ││                     │
│  src/lib/Settings.svelte (Updates section)         ││                     │
│  src/lib/Toolbar.svelte (badge on Settings gear)   ││                     │
│  src/App.svelte (startup check + state)            ││                     │
└────────────────────────────────────────────────────┘└─────────────────────┘
                            │
                            ▼  (one HTTPS GET on launch)
        https://github.com/pndaza/just-ocr/releases/latest/download/latest.json
                            │
                            ▼  (served by tauri-action, auto-generated)
                  GitHub Release assets:
                    latest.json   ← version + per-target download URLs + sigs
                    *.sig         ← signature per updater bundle
                    *.dmg/.msi/.AppImage (updater artifacts)
```

### Data model (`src/lib/updater.ts`)

```ts
import { check } from "@tauri-apps/plugin-updater";
import { relaunch } from "@tauri-apps/plugin-process";
import { getVersion } from "@tauri-apps/api/app";

/** All states the update UI can be in. */
export type UpdateStatus =
  | { kind: "idle" }
  | { kind: "checking" }
  | { kind: "up-to-date" }
  | { kind: "available"; version: string }   // update exists, not yet installing
  | { kind: "downloading"; percent: number }
  | { kind: "installing" }
  | { kind: "error"; message: string };

export interface AvailableUpdate {
  version: string;          // e.g. "0.4.0"
  /** The plugin's Update object; kept so downloadAndInstall can act on it. */
  // (opaque to UI; held in module state)
}

/** Silent startup check. Errors are swallowed. Calls onResult only on success. */
export async function checkForUpdateSilent(onAvailable: (v: string) => void): Promise<void>;

/** Manual check. Errors propagate as an UpdateStatus for inline display. */
export async function checkForUpdate(): Promise<UpdateStatus>;

/** Download + install the most-recently-found update, then relaunch. */
export async function downloadAndInstall(onProgress: (percent: number) => void): Promise<void>;

/** Current app version (e.g. "0.3.0"). */
export async function getAppVersion(): Promise<string>;
```

Module holds the resolved `Update` object in module-level state between a
successful `checkForUpdate()` and the subsequent `downloadAndInstall()` call.

### Surfacing: Settings gear badge

The Toolbar's existing Settings gear (`.icon-btn`) gains a small accent-colored
dot via a `::after` pseudo-element when `updateAvailable` is truthy. No new
component, no toast system, no modal-blocking notification — just a discoverable
visual hint that resolves into the full update UI when the user opens Settings.

```css
.icon-btn.has-update::after {
  content: "";
  position: absolute;
  top: 2px; right: 2px;
  width: 7px; height: 7px;
  background: var(--accent);
  border-radius: 50%;
  border: 1.5px solid var(--bg-elev);   /* punch-through so the dot reads on the gear */
}
```

### Startup-check flow

```
App.svelte onMount:
  fire-and-forget checkForUpdateSilent(v => updateAvailable = v)
    ├─ network error / signature error / parse error
    │     → console.warn(...); do NOT set updateAvailable; UI unchanged
    ├─ up-to-date
    │     → UI unchanged
    └─ available
          → updateAvailable = version
          → Toolbar receives updateAvailable prop → gear shows badge
          → (if Settings modal is already open) its Updates section reflects it
```

The check is **not awaited** on mount — it must never block app startup or
language loading. `loadLanguages()` and the startup check run concurrently.

### Settings modal — Updates section

A new `<section class="sec">` below "Theme", reusing the existing modal's `.sec`
/ `.lbl` classes. Contents depend on the *manual* check status (separate state
from the silent startup result — the manual button always reflects its own
operation):

| Manual status | UI |
|---|---|
| `idle` | "Check for updates" button (and current version string always shown) |
| `checking` | "Checking…" disabled button |
| `up-to-date` | "Just OCR is up to date ✓" (fades to idle after a few seconds) |
| `available` | "vX.Y.Z available" + **"Download & install"** button |
| `downloading` | progress bar + "Downloading… NN%" |
| `installing` | "Installing…" |
| `error` | red inline message + reset to idle |

When the Settings modal opens, if a startup check already found an update, the
section pre-populates with the `available` state (so the user doesn't have to
re-check).

## Changes by file

### Backend (Rust)

**`src-tauri/Cargo.toml`** — add two deps:
```toml
tauri-plugin-updater = "2"
tauri-plugin-process = "2"   # relaunch() after install
```

**`src/lib.rs`** — register both plugins in `run()`, alongside the existing
`tauri_plugin_opener::init()`. Because `#[cfg(desktop)]` cannot be attached
mid-builder-chain, the conditional registration breaks out of the chain:

```rust
let mut builder = tauri::Builder::default()
    .plugin(tauri_plugin_dialog::init())
    .plugin(tauri_plugin_fs::init())
    .plugin(tauri_plugin_opener::init());

// Updater + process (relaunch) are desktop-only. This is a desktop app, so the
// cfg gate is defensive/documentation rather than strictly necessary — it
// matches the official Tauri pattern and keeps a future mobile target clean.
#[cfg(desktop)]
{
    builder = builder
        .plugin(tauri_plugin_updater::Builder::new().build())
        .plugin(tauri_plugin_process::init());
}
```

The rest of the builder (`invoke_handler`, `setup`, `.run(...)`) chains off
`builder` as before. The plan will show the full integrated `run()` body.

**No new `invoke` command.** The frontend talks to the updater via the plugin's
own JS API, so the `invoke_handler` list is unchanged.

### Capabilities

**`src-tauri/capabilities/default.json`** — add the updater + process default
permission sets. The exact identifier for each plugin's default set is
`<plugin>:default` (e.g. `updater:default`, `process:default`); the version read
uses a core app permission whose identifier should be confirmed against the
generated schema at implementation time (`../gen/schemas/desktop-schema.json`):
```json
"updater:default",
"process:default"
// + the core app-version read permission (verify identifier in schema)
```

### Frontend

**`src/lib/updater.ts`** (new) — typed wrapper around the updater + process
plugins, as specified in §Data model. Single home for all update-related Tauri
calls (mirrors the `ocr.ts` convention).

**`src/App.svelte`** —
- New state: `let updateAvailable = $state<string | null>(null);`
- On mount, fire `checkForUpdateSilent` (concurrent with `loadLanguages()`).
- Pass `updateAvailable` to `Toolbar` (for the gear badge) and to `Settings`
  (to pre-populate its Updates section).

**`src/lib/Toolbar.svelte`** —
- New prop: `updateAvailable: string | null`.
- Settings gear gets `class:has-update={!!updateAvailable}` + the `::after`
  badge style. `position: relative` already implied by flex centering; add
  explicitly if needed.

**`src/lib/Settings.svelte`** —
- New prop: `updateAvailable: string | null`.
- New `<section class="sec">` for Updates: version string, manual check button,
  status display, download/install button + progress bar.
- Local state for the *manual* check's `UpdateStatus` (separate from the
  startup `updateAvailable` prop, so opening Settings never re-fires the
  startup check).

### Configuration

**`src-tauri/tauri.conf.json`**:
```jsonc
{
  "bundle": {
    "createUpdaterArtifacts": true
  },
  "plugins": {
    "updater": {
      "pubkey": "<contents of just-ocr.updater.pubkey.pem>",
      "endpoints": [
        "https://github.com/pndaza/just-ocr/releases/latest/download/latest.json"
      ]
    }
  }
}
```
The `pubkey` value is the literal PEM string generated by
`cargo tauri signer generate` — **not a file path** (Tauri rejects paths).

### Release CI

**`.github/workflows/release.yml`** — two changes:
1. Add signing secrets to the `tauri-action` env:
   ```yaml
   env:
     GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
     TAURI_SIGNING_PRIVATE_KEY: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY }}
     TAURI_SIGNING_PRIVATE_KEY_PASSWORD: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY_PASSWORD }}
     CFLAGS: ...
     CXXFLAGS: ...
   ```
   `tauri-action` already uploads `latest.json` + `.sig` files by default
   (`uploadUpdaterJson: true`, `uploadUpdaterSignatures: true`) — no new inputs
   needed.
2. Flip `releaseDraft: true` → `releaseDraft: false` (auto-publish). With
   auto-publish, the `/releases/latest/download/latest.json` endpoint resolves
   immediately on green CI, and existing clients start finding the update.

**`AGENTS.md`** — extend the "Release" section with: signing-secret location,

## Security

- **Signature verification is mandatory and cannot be disabled.** The updater
  verifies each downloaded bundle against the pubkey in `tauri.conf.json` before
  installing. A tampered bundle fails the signature check and is rejected.
- **Private key handling.** `TAURI_SIGNING_PRIVATE_KEY` lives only as a GitHub
  Actions repository secret. It is **never** committed, **never** logged, and
  exists nowhere else. If lost, **no further updates can ever be published** to
  existing installs — the keypair must be backed up securely outside the repo
  (e.g. a password manager, offline storage) at generation time.
- **Endpoint trust.** TLS is enforced (the endpoint is HTTPS). GitHub serves the
  manifest; there is no self-hosted server to compromise. A malicious or
  hijacked release would still need the private key to produce a validly-signed
  bundle.
- **No telemetry.** The single network call fetches `latest.json` only. No
  version ping-back, no analytics, no usage data leaves the client.

## Testing

### Unit-testable without a live release

- **`updater.ts` state mapping** — the pure logic that translates plugin
  results/events into `UpdateStatus` values. This is the bulk of the
  client-side logic and has no network dependency. Covers: up-to-date,
  available, download-progress percent computation, error wrapping.
  (Mirrors the `ocr.test.ts` / `result.test.ts` pattern.)

### Manual / end-to-end (cannot be cleanly automated)

- **Happy path, per platform:** install an *older* build, publish a newer
  release, open the app, confirm the gear badge appears, open Settings, confirm
  the version shows, click "Download & install", confirm progress + relaunch +
  new version runs. Repeat for macOS (aarch64 + x86_64), Linux, Windows.
- **Offline launch:** disconnect network, open app, confirm **no** error UI, no
  badge, app fully functional (silent-failure rule).
- **Manual check while offline:** open Settings, click "Check for updates",
  confirm a friendly inline error message (visible-failure rule).
- **Up-to-date:** open Settings on the latest version, click "Check", confirm
  "Just OCR is up to date ✓".
- **Signature mismatch / corrupt manifest:** point endpoint at a bad fixture,
  confirm the download is rejected with an inline error (manual path) or
  swallowed (startup path).

### A local end-to-end dry run (for development)

Because the live endpoint only serves *published* releases, dev verification
uses a local manifest:
1. Generate a dev keypair (`cargo tauri signer generate`).
2. Build with `TAURI_SIGNING_PRIVATE_KEY` set, `createUpdaterArtifacts: true`.
3. Serve a hand-written `latest.json` + the signed bundle over local HTTPS (or
   use `dangerousInsecureTransportProtocol: true` for `http://localhost` in a
   dev-only config override).
4. Bump the version down, run, and trigger the check against the local
   endpoint.

This is documented in the implementation plan; it is not part of CI.

## Risk register

| Risk | Mitigation |
|---|---|
| **Private key lost** → no future updates shipable | Backup key outside repo at generation; document in `AGENTS.md` |
| **Auto-publish ships a broken bundle** (no manual gate) | Accepted trade-off; `fail-fast: false` surfaces every platform failure before the release is created. Consider a follow-up to re-add a publish gate if breakage recurs. |
| **macOS code-signing/notarization for the updater bundle** | Out of scope for this spec — the app is currently unsigned/ad-hoc; updater works with Tauri's signature alone. Notarization is a separate, future hardening step. |
| **Windows auto-exit on install** loses unsaved state | The app has no persistent unsaved state (OCR results are in-memory, ephemeral). Acceptable; documented in the Updates UI copy ("will restart"). |
| **First-run old-build migration** — users on 0.3.0 won't auto-update to 0.4.0 because 0.3.0 has no updater | Bootstrap problem: 0.3.0 users must manually download 0.4.0 once; from 0.4.0 onward auto-update works. Unavoidable for any updater's first release. |
| **Rate limits on GitHub Releases manifest** | One GET per launch per user; GitHub's release asset CDN handles this volume easily. Not a concern at this scale. |

## Out of scope

- Background download while the app runs (the two-step flow downloads only on
  explicit click).
- Delta updates (Tauri updater downloads full bundles).
- Update channels / betas (single `latest` track only).
- macOS notarization / Apple Developer ID signing (separate hardening effort).
- Migration UX for pre-updater installs (manual one-time download accepted).
